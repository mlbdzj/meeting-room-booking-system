# 智能会议室预约系统 · 面试准备手册

## 一、项目定位

这是一个基于 Agent 的会议空间预约系统，使用 FastAPI + SQLAlchemy + MySQL 提供后端，React 19 + TypeScript + Vite 提供前端。系统同时支持页面预约与自然语言预约，覆盖空间、会议室、时段库存、容量、审核、取消、统计和知识库。

核心设计目标：

1. AI 能理解自然语言，但业务规则由确定性代码执行；
2. 页面与 Agent 共用同一套预约校验；
3. 待确认与已确认预约都占用会议室余量；
4. Agent 工具层内建权限控制，提示词不能替代权限；
5. 大模型不可用时仍能使用本地规则和知识库。

## 二、一分钟项目介绍

> 我做了一个会议室预约系统，页面预约和 AI 预约共用同一个 `reservation_service`。预约使用开始、结束时间记录占用，库存按半开区间重叠统计，待确认和已确认都会占用余量。AI 侧使用 function calling 查询空间、实时余量、个人预约和规则；真正预约时先生成服务端草稿，用户确认后再复用页面同一套校验写库，避免模型误判和重复提交。大模型异常时会自动降级到本地知识库，权限控制放在工具内部。

## 三、Agent 设计

### 1. 为什么不让模型直接写数据库

模型适合理解“下周五上午 10 点到 12 点、西湖 A、10 人”这样的口语描述，但不适合保证金额、权限和库存一致性。系统采用两段式：

1. `prepare_reservation` 解析并生成草稿，只校验、不提交；
2. 用户点击“确认预约”后，后端基于服务端保存的草稿重新执行完整校验；
3. 校验通过后创建状态为 `pending` 的预约；
4. 同一消息只能确认一次，保证幂等。

前端确认接口只传 `session_id` 和 `message_id`，不能传金额、空间或会议室，避免篡改。

### 2. 工具与权限

| 工具 | 权限 |
| --- | --- |
| `search_knowledge` | 登录用户 |
| `list_venues` | 登录用户 |
| `check_meeting_room_availability` | 登录用户 |
| `list_my_reservations` | 只查当前用户 |
| `list_pending_reservations` | 仅管理员 |
| `system_statistics` | 管理员全量；会员本人范围 |
| `reservation_rules` | 登录用户 |
| `prepare_reservation` | 登录用户 |

权限写在 handler 中，不依赖模型遵守提示词。即使模型被诱导调用管理员工具，工具也会拒绝返回越权数据。

### 3. 本地降级

`answer_question` 优先尝试大模型。未配置密钥、网络失败、超时或模型没有返回有效内容时，自动使用本地规则引擎和知识库。回复来源会显示给前端，便于用户判断数据来源。

### 4. 自然语言解析

- 日期：今天、明天、下周五、11 月 6 日、ISO 日期；
- 时间：10 点到 12 点、下午 2 点到 4 点、9:30-11:30；
- 时长：两小时、2.5 小时、90 分钟、半天、全天；
- 会议室：完整名称、简称、布局名称；
- 规模：两间、10 人；
- 设备：需要视频会议、额外白板、茶歇等。

## 四、库存与并发

### 1. 时段重叠

预约区间是左闭右开 `[start_at, end_at)`：

```sql
WHERE meeting_room_id = :room_id
  AND status IN ('pending', 'confirmed')
  AND start_at < :query_end
  AND end_at > :query_start
```

如果上一场 10:00-12:00，下一场 12:00-14:00，`12:00 < 12:00` 不成立，所以不会误判冲突。

### 2. 剩余数量

```text
remaining = meeting_room.quantity - SUM(overlapping_reservation.rooms)
```

确认预约时排除自己的 ID 再做一次校验，防止从提交到审核之间被其他预约占满。

### 3. 生产环境如何强化

当前实现适合单机演示。生产环境可增加：

1. 锁定会议室行 `SELECT ... FOR UPDATE`；
2. 为时段库存建立独立表并条件更新；
3. 在数据库层增加唯一约束或排他约束；
4. 对高频空间做 Redis 短时锁和热点缓存；
5. 写入失败返回可重试错误，不使用模型自动重试写操作。

## 五、计费与容量

- 时长按分钟计算后转为小时，支持半小时和 90 分钟；
- 总价使用 `Decimal` 计算：`hourly_price × hours × rooms`；
- 参会人数不能超过 `capacity × rooms`；
- 预约时间必须处于空间每天的开放时段内；
- 历史预约保存金额快照，之后修改时租价不会影响已有记录。

## 六、数据库设计

主要实体：

- `venue`：会议空间、地址、开放时段、状态；
- `meeting_room`：空间下的会议室规格、布局、时租价、容量、数量、设备；
- `reservation`：预约人、空间、会议室、起止时间、时长、间数、人数、金额和状态；
- `sys_user`：管理员与会员；
- `knowledge`：客服问答；
- `chat_session` / `chat_message`：Agent 会话与操作卡片。

常用索引包括 `venue_id`、`meeting_room_id`、`user_id`、`start_at`、`end_at` 和 `status`。

## 七、状态机

```text
pending -> confirmed / rejected / canceled
confirmed -> completed / canceled
```

- 待确认与已确认占用库存；
- 拒绝与取消释放库存；
- 已确认且结束时间已过，自动转已完成；
- 已完成、已拒绝、已取消不能取消或重复审核。

## 八、前端设计

- React Router 负责页面与角色守卫；
- Zustand 保存登录态；
- 空间页按角色显示卡片或表格；
- 会议室弹窗根据时间和空间请求实时余量；
- 预约审核页默认显示全部状态，待确认优先；
- Agent 使用悬浮窗，支持会话历史、知识库推荐问题和预约确认卡。

## 十、可继续回答的问题

**为什么选择 FastAPI？**
异步生态完整、Pydantic 类型校验清晰，自动生成 OpenAPI 文档，适合前后端协作与 Agent 工具 schema。

**为什么 Agent 工具使用 Pydantic？**
模型传参不可信，Pydantic 统一做类型和枚举校验；错误会作为工具结果返回给模型，由模型重新组织参数，而不是直接 500。

**如何避免 N+1？**
预约序列化时按 ID 集合批量查询空间、会议室和用户名称，再通过字典映射组装。

**会议室库存和传统住宿房间库存有什么不同？**
会议室通常按小时使用，时间精度更高，容量和设备差异更明显；因此本项目改为 `start_at/end_at` 时间区间、时租价和设备需求，而不是按晚数和床型。

**系统最大的改进方向是什么？**
把数据库层面的并发约束补上，并增加提醒、日历订阅、设备准备和费用结算能力。
